# 排查记录：一次「日志摘要」误判

> 版本：1.7.0 → 1.8.0 ｜ 时间：2026-11-24 ｜ 影响：详情页失败原因显示错误，可能误导排查方向

## 一、现象

用户打开 `/runs/5`（CI #4，Java 构建失败），红色摘要卡片给出：

```
[测试失败] 来自 job: Java · 构建与单元测试
6 处测试失败
  ① 权限不足 ×2   第 265 行  WARN ... status=401 Bad credentials
  ② 权限不足 ×2   第 376 行  WARN ... status=403 Resource not accessible
  ③ 测试失败      第 424 行  [ERROR] Tests run: 13, Failures: 1 ...
  ④ 测试失败      第 1104 行 [ERROR] Tests run: 302, Failures: 3 ...
```

四个问题：

| # | 现象 | 实际情况 |
|---|---|---|
| 1 | 点「查看错误原文」打开抽屉，日志区空白 | 日志已加载，模板判断条件写错 |
| 2 | 摘要内容全是 `Tests run: ...` 这类记账行 | 真正的失败在下一行，被丢掉了 |
| 3 | 抽屉底部文字在深色背景上看不清 | 摘要样式按浅色背景设计 |
| 4 | 说 6 处失败，只展示 4 条 | 计数把 Maven 的子集汇总重复累加 |

**用户的实际感受**：`权限不足` 会让人去查 token，而真实原因是三个单元测试断言失败——**错误的结论比没有结论更糟**。

## 二、根因

### 2.1 摘要指向了「记账行」

Maven surefire 的一次失败会输出四层信息：

```
[ERROR] Tests run: 13, Failures: 1, ... <<< FAILURE! -- in RunWriteServiceTest$CommitEnrichment   ← 逐类汇总（记账）
[ERROR] RunWriteServiceTest.updatesExistingRun -- Time elapsed: 0.013 s <<< FAILURE!             ← 具体哪个测试
Wanted but not invoked:                                                                          ← 真正原因
runMapper.updateById(
...
[ERROR] Tests run: 302, Failures: 3, Errors: 0, Skipped: 0                                       ← run 级总计
```

原实现把「逐类汇总」当成错误条目，而它只说明"哪个类挂了"，不说明"为什么挂"。

### 2.2 计数把子集当独立项

```
逐类汇总：Failures: 1 + 1 + 1
run 级总计：Failures: 3          ← 已经包含上面三个
原实现：全部相加 = 6              ❌
```

### 2.3 证据不对等，却在平等投票

同一条日志里混着两种东西：

| 行 | 性质 | 原实现当成 |
|---|---|---|
| `Tests run: 13, Failures: 1` | 测试框架的权威结论 | 一条普通命中 |
| `WARN ... status=401 Bad credentials` | **被测代码打印的预期内日志**（测试的就是鉴权失败分支） | 一条真权限错误 |

按出现次数投票时，4 条 WARN 压过了 1 条真结论。

### 2.4 前端两处

- 模板写的是 `v-else-if="digest"`，而「从摘要点进来」只加载了全文、`digest` 为 `null` → 落进空状态分支
- 摘要卡片配色是 `#1d2129` 文字 + `#eef0f4` 边框，但容器背景是 `#0f1729`

## 三、修复

### 3.1 引入三级证据模型

| 等级 | 例子 | 作用 |
|---|---|---|
| **authoritative** | run 级 `Tests run: N, Failures: M`、pytest `2 failed` | 决定类别与**数量** |
| **primary** | `Class.method -- Time elapsed ... <<< FAILURE!`、`FAILED x.py`、`npm error` | 决定 highlights |
| **detail** | `Wanted but not invoked:`、`AssertionFailedError`、`E assert` | 附到主错误后面 |
| **meta** | 逐类汇总 `Tests run: ... -- in ClassName` | 记账，不进摘要 |

配套规则：

1. 数量取 run 级总计的**最大值**（不是求和）
2. 权威汇总行在有具体错误时不占摘要位，只用于定类别与数量
3. 摘要正文 = 测试方法名 + 紧随其后的 1~2 行说明
4. 排序：同类错误排前，噪声不占第一眼

### 3.2 前端

| 问题 | 改法 |
|---|---|
| 抽屉空白 | 条件改为 `v-else-if="digest \|\| logLines.length"` |
| 深色背景看不清 | 摘要卡片改深色主题（`rgba(255,255,255,.04)` 底 + 亮色文字） |
| 底部提示不明显 | 改为「共 N 行 · 折叠 M 行」+ 蓝色可点「查看全文 →」 |
| 卡片太长 | 默认 2 条 + 右下角「展开全部 N 条 / 收起」 |

## 五、沉淀：编译期常量内联

### 现象

改了 `LogDigestCodec.VERSION` 2 → 3，测试出现两个**互相矛盾**的失败：

```
roundTrip              : 期望有值，却是空
versionMismatchIsMiss  : 期望为空，却有值
```

### 最小复现

```java
public class A { public static final int VERSION = 2; }
System.out.println("读到 " + A.VERSION);
System.out.println("算出的 " + (A.VERSION + 1));
```

把 A 改成 3，**只重编 A**，再跑没重编的 B：

```
读到 2      ← 旧值
算出的 3    ← 恰好等于新的真实值
```

字节码印证：值已经被固化成字符串常量，压根没有"读取字段"这个动作。

```
ldc  #15   // String 读到 VERSION      = 2
ldc  #23   // String 算出的 VERSION + 1 = 3
```

### 原理

JLS 称 `final` + 基本类型/String + 常量表达式初始化的变量为 **constant variable**。javac 编译**使用方**时直接内联其值。所以改常量后，所有使用方都必须重编。

Maven 增量编译只重编改动的源文件 → `target/classes` 是新的，`target/test-classes` 还是旧的。

### 指纹

**一个"该有的没有"、一个"该没有的却有"**——这种镜像式反常失败，基本就是常量内联，不要先怀疑业务逻辑。

### 应对

| 方案 | 说明 |
|---|---|
| 纪律 | 改这类常量后 `rm -rf target/test-classes && mvn test` |
| **推荐** | 改用方法 `public static int version() { return 3; }`，永远不会被编译期内联 |
| 次选 | 改包装类型 `static final Integer`，但注意 `!=` 会变成引用比较，必须用 `equals` |

会被内联：`static final int/String`；不会被内联：包装类型、非 final、方法调用、枚举。

## 六、可复用的排查经验

1. **摘要给错结论比不给结论更糟**——用户会照着错方向去查，浪费的时间远超"没有摘要"
2. **先复现再修**：把现场日志存成固定用例，先跑出错误输出，再改代码看变化
3. **降级不等于排除**：把噪声标为 `detail` 后，它仍会被"该类别没有更强证据时展示"的兜底捞回来，必须显式 `excluded`
4. **镜像式反常失败 = 环境/编译问题**，不是逻辑问题
